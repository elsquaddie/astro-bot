# AstroBot Telegram-First MVP Features

Дата: 2026-05-09

## Видение

AstroBot должен помогать человеку не пропускать события в небе: затмения, метеорные потоки, суперлуния, редкие сближения и хорошие моменты для наблюдения в телескоп. Ценность не в 3D-картинке, а в простом обещании: бот заранее скажет, что стоит увидеть, где это будет видно, насколько хорошие условия, и когда лучше выйти на улицу.

Продуктовый тон: не академический каталог событий, а личный помощник для наблюдений. Примеры сценариев:

- Человек не хочет снова пропустить затмение.
- Человек планирует романтический вечер под звездопад.
- Человек смотрит в телескоп и хочет знать, когда планеты, Луна или затмения будут интересны.
- Человек хочет иногда оторваться от монитора и понять: "сегодня правда стоит посмотреть на небо".

## Текущее состояние

- Telegram-бот умеет сохранять Telegram location, показывать `/today` и открывать `/settings`.
- Текстовый ввод города не реализован: если пользователь напишет "Самара", "Абу Даби", "Нью-Йорк" или "Монте-Карло", бот сейчас ничего не сделает.
- Visibility cache строится отдельным worker-ом. Если локация новая и cache еще не посчитан, пользователь может увидеть "No visible astronomical events in the next 7 days", хотя система просто еще не рассчитала видимость для этой точки.
- 3D-визуализация и календарь были полезным исследовательским прототипом, но не являются ядром MVP.

## Feature 1: Telegram-first режим и отключение 3D/calendar

Цель: сделать Telegram-бот главным продуктом, а 3D frontend и visual calendar оставить как отключенный прототип.

Решение:

- Добавить `ENABLE_WEB_UI=false` по умолчанию.
- Добавить `ENABLE_SOLAR_SYSTEM_API=false` по умолчанию.
- При выключенных flags:
  - не монтировать `frontend/` на `/`;
  - не подключать `/api/solar-system`;
  - не позиционировать README вокруг 3D UI.
- Код frontend не удалять, чтобы можно было вернуться к нему позже.

Критерий готовности:

- API health/readiness и Telegram bot продолжают работать.
- `/api/solar-system` и `/` недоступны по умолчанию.
- Включение flags возвращает старое поведение для прототипа.

## Feature 2: Город как нормальный способ выбора локации

Цель: пользователь может написать город вместо отправки GPS.

Рекомендуемый сервис: Open-Meteo Geocoding API.

Почему он подходит:

- Поддерживает глобальный поиск локаций на разных языках.
- Возвращает координаты, timezone, страну, регион и population.
- Не требует API key для open-access/non-commercial использования.
- Имеет тот же ecosystem, что и weather forecast API.

UX:

1. Пользователь пишет: `Самара`.
2. Бот ищет варианты.
3. Если найден один уверенный вариант:
   - "Нашел: Самара, Самарская область, Россия. Использовать этот город?"
4. Если найдено несколько:
   - "Что ты имел в виду?"
   - кнопки: "Самара, Россия", "Samarra, Iraq", "Samara, Costa Rica".
5. После выбора бот сохраняет координаты и timezone.
6. Бот сразу говорит, что он проверяет ближайшие события для этой локации.

Критерий готовности:

- `Самара`, `Abu Dhabi`, `New York`, `Monte Carlo` находят корректные варианты или дают понятное "не нашел, попробуй уточнить страну".
- Пользователь не обязан делиться точным GPS, если хочет использовать город.

## Feature 3: Правильный UX для visibility cache

Цель: cache miss не должен выглядеть как отсутствие событий.

Текущая проблема:

- Локация сохраняется сразу.
- Visibility cache считается worker-ом отдельно.
- `/today` читает только cache.
- Если cache пустой, бот говорит "событий нет".

Новый UX:

- После выбора локации бот отвечает: "Считаю, что будет видно из Самары. Это может занять несколько секунд."
- Система запускает расчет видимости для новой локации сразу, а не ждет суточного worker job.
- Если расчет быстрый, бот сразу показывает ближайшие интересные события.
- Если расчет занимает больше нескольких секунд, бот пишет: "Я досчитаю и пришлю результат отдельным сообщением."
- `/today` различает:
  - "событий действительно нет";
  - "локация есть, но видимость еще не посчитана";
  - "нет данных о событиях на выбранный период".

Критерий готовности:

- Новый пользователь после выбора города или GPS не получает ложное "событий нет".
- Worker остается для регулярного пересчета, но user-facing flow умеет считать on demand.

## Feature 4: Условия наблюдения через погоду

Цель: показывать не только "событие геометрически видно", но и "стоит ли выходить смотреть".

Рекомендуемый сервис: Open-Meteo Weather Forecast API.

Почему он подходит:

- Дает forecast до 16 дней.
- Поддерживает hourly variables: cloud cover, precipitation probability, weather code, visibility, wind speed.
- Для MVP не требует API key в open-access режиме.
- Для коммерческого/надежного production режима можно перейти на customer API key.

MVP scoring:

- `excellent`: облачность низкая, осадки маловероятны, видимость хорошая.
- `ok`: условия средние, событие стоит держать в уме.
- `poor`: облачность/осадки/видимость плохие, лучше предупредить пользователя.
- `unknown`: событие дальше горизонта прогноза погоды, например дальше 16 дней.

Пример сообщения:

> Завтра в 21:00 в Самаре будет видно суперлуние. Условия: хорошие, облачность около 20%, осадки маловероятны. Напомнить за час?

Ограничение:

- Прогноз погоды не должен блокировать астрономическое уведомление. Если weather API недоступен, бот все равно сообщает событие и честно пишет: "Погоду проверить не удалось".

## Feature 5: Человеческие настройки уведомлений

Цель: заменить техническое деление "rare/regular" на понятные режимы.

Предлагаемые режимы:

- `Редкие события`: солнечные и лунные затмения, редкие покрытия, заметные сближения.
- `Романтичные вечера`: суперлуние, яркие метеорные потоки, красивые ночные события.
- `Телескоп`: планеты, Луна, близкие сближения, лучшие окна наблюдения.
- `Все интересное`: широкая подписка, но с защитой от спама.

Настройки времени:

- За 1 день.
- За 3 часа.
- За 1 час.
- В момент "лучшего окна наблюдения", если оно известно.

Критерий готовности:

- Пользователь понимает настройки без знания классов событий.
- Уведомление содержит: событие, город, локальное время, насколько хорошо видно, погодные условия, действие.

## Feature 6: Мультиязычный Telegram UX

Цель: бот должен быть пригоден для пользователей из разных стран без архитектурной переделки.

MVP языки:

- `ru` — русский;
- `en` — английский;
- fallback — английский.

Решение:

- Сохранять язык пользователя в `users.language_code`.
- На `/start` брать язык из Telegram `from_user.language_code`.
- Добавить `/language` для ручного переключения.
- Вынести тексты Telegram-бота в переводные ключи.
- Передавать язык пользователя в geocoding API, чтобы названия городов возвращались в подходящей локали, если провайдер это поддерживает.
- Хранить астрономические события языконезависимо: `meteor_peak`, `lunar_eclipse`, `supermoon`, а переводить только в интерфейсе.

Критерий готовности:

- Русский пользователь видит `/start`, выбор города, `/today`, `/settings` и `/language` на русском.
- Английский пользователь видит те же сценарии на английском.
- Все переводные ключи существуют одновременно в `ru` и `en`.
- Неизвестный язык, например `de`, безопасно падает в английский.

## Рекомендуемый порядок реализации

1. Отключить 3D frontend/calendar через feature flags.
2. Добавить geocoding для городов.
3. Исправить cache-miss flow и on-demand расчет видимости.
4. Добавить weather-aware observation conditions.
5. Переписать `/settings` в человеческие режимы уведомлений.
6. Добавить мультиязычный Telegram UX для `ru/en`.
7. Обновить README под Telegram-first MVP.
